# Reviewed eligibility for existing VM boot devices

Continue the approved stage-1 hardware roadmap by allowing an existing explicit QEMU boot order to enable or disable supported, already configured devices. Keep the reviewed boot-order workflow and its source, readiness, typed-confirmation and uncertain-outcome protections. Use fixtures now; actual PVE 8/9 SeaBIOS/OVMF/media/PXE/startup validation remains pending. This increment does not complete hardware or boot administration.

## Approaches and coordinator choices

Extend the current explicit-order review engine and dialog with eligibility controls. It already reads the full configured device set, hashes boot-relevant source data and submits only boot+digest. This keeps one clear review and one native write. A separate eligibility endpoint/dialog would duplicate admission/recovery and could race an order edit, so it is not chosen. Converting default/legacy boot modes would normalize implicit settings and potentially remove bootdisk; keep that as later work. These are coordinator choices under the ongoing authorized roadmap, not new user-specific preferences.

## Scope and native behavior

Only stopped QEMU VMs whose current boot property is an unambiguous nonempty explicit order of supported configured devices qualify. An existing order with one device now qualifies. The proposed order must contain 1–89 distinct supported configured device IDs and differ from the current order or membership. Only explicit inclusion/exclusion and priorities change. Do not attach, detach, remove or rewrite disks/NICs/media, edit firmware, clear bootdisk, convert legacy/default settings, stop/start guests or invoke SSH. Unsupported/missing enabled entries make the whole source read-only; never silently drop them as a repair.

Reuse ordinary device classification from the first boot increment: bounded IDE/SATA/SCSI/VirtIO storage-backed disks, configured storage ISO CD-ROMs and ordinary configured net0–31 NICs. Preserve all raw options and identities. Host/empty/cloud-init/passthrough/unsupported devices, EFI/TPM/unused/USB/PCI remain unselectable. Ordinary ISO named cloudinit.iso stays an ISO under the exact native cloud-init predicate. Eligibility describes a supported configured target, not media availability or proven bootability. A disconnected NIC keeps its warning. Boot eligibility is distinct from NIC link state and hardware attachment.

Keep all existing lock/template/HA/pending/snapshot/node/task-visibility guards, exact-node Sys.Audit and native VM.Config.Disk authority. Presence of bootdisk, custom args or visible legacy/native-cleanup hazards blocks the change. Native PUT still submits exactly boot:'order='+target.join(';') plus digest and must return null. Fresh postconditions require the target order, retained configured device identities, all unrelated returned current-config values, stopped readiness and connection revision. Unknown/partial/read failures stay consumed and unconfirmed with no retry, rollback, power action or invented task/log. Preserve existing API-visible guarantees; masked secrets, hidden sections and physical file comments are not observable.

## Inventory and review contract

Extend the current inventory with eligibleDevices:BootDevice[], deterministically sorted by device ID. It includes every supported configured candidate regardless of current boot eligibility, and must include supported current enabled devices with exactly matching identity/kind/label. Keep order:BootDevice[] as the current enabled sequence. Excluded contains configured unsupported/nonboot devices, with reasons; ordinary disabled candidates belong in eligibleDevices rather than excluded. Unsupported current entries remain visible in order but make ready=false. sourceIdentity binds the entire configured device/firmware/boot-relevant set, including disabled candidates, plus guest/name, as before. Do not expose raw device options, notes, secret values or guest IP/DNS/ipconfig addressing through the added inventory. Existing authenticated UI NIC summaries (model, MAC, bridge, VLAN) also identify disabled NIC candidates; these summaries are never provider requests.

Review input remains strict {sourceIdentity,order:string[]}; reject empty, duplicate, absent/unselectable IDs and no-op, while accepting valid subsets/supersets/permutations of the configured eligible IDs. Review output adds eligibleDevices:BootDevice[] and retains currentOrder/proposedOrder. Proposed rows come from the full eligible inventory, not only the old enabled sequence. Five-minute single-use reviews bind target order, native digest, source/guest/name and connection revision. Replacing an initially disabled candidate before review or execute is a source conflict with no PUT. Reservations, revision races, expiry and cached historical verified results remain unchanged.

The new frontend must remain compatible with the prior agent: absent eligibleDevices means reordering the original enabled set only, with its original minimum of two enabled devices. Membership controls remain unavailable and advise updating the agent. Never infer extra candidates from flattened insights or silently submit additions to an older agent. Only an absent field selects legacy mode; a supplied null, malformed/duplicate/unsupported candidate, missing current member or identity mismatch makes all editing read-only. For a modern inventory, validate the server review's full eligible set and current/proposed identities against the fixed opening selection/draft; mismatches require close/reselection. A protocol capability change during refresh/review also requires close/reselection. Legacy review responses remain usable only for the legacy membership-preserving draft and matching absent-field contract. Existing older clients remain safe because their original permutation requests are still valid.

Use a small pure web/src/lib/boot-order.ts contract helper shared by card/dialog to validate candidate rows, unique complete current-member coverage, inventory/review capability consistency and order/identity equality. Frontend types allow an absent eligibleDevices field for prior agents; server inventory/review always supplies it. Validate row IDs/identity/kind/labels rather than reimplementing native property parsing. Server fixture tests establish completeness of disabled candidates; the browser cannot prove the existence of unseen configuration keys.

## UI and review

Keep the on-demand QEMU card, existing dialog, focus behavior, warm glass themes and 390px bounds. Show supported configured devices with explicit draft inclusion controls and priority arrows for enabled rows. Enabling appends to the current draft; disabling removes only boot eligibility and retains every other priority. Keep the focused device/control reachable after either action and announce its changed eligibility/position. Users may temporarily leave an empty draft, but review is disabled with a clear requirement to enable at least one device; the server independently rejects empty targets.

Show before/after enabled priorities and explicit newly enabled/disabled devices with labels before typed native-name confirmation. Pure reorder says the enabled set is unchanged. Explain that hardware stays attached, network link state is unchanged and the next start may enter another OS/installer or fail. Native docs require every software-RAID boot member to remain enabled; SeaBIOS/OVMF initialize marked boot disks before the OS loads. Warn users to keep every disk needed to load their bootloader/OS enabled, including software-RAID members. Do not infer a guest RAID layout or automatically disable another device. For configured OVMF NIC candidates without rng0, carry a targeted VirtIO RNG/PXE-prerequisite caution from the stock editor, without automatically attaching RNG or promising PXE. Preserve disconnected-NIC warnings alongside this caution. The pinned PVE9 editor requires RNG while the pinned PVE8 editor has no such warning; use conditional cross-version wording and never claim PXE validation.

Retain stale drafts and require a fresh inspect/review after known409; replaced source/candidate identity requires close/reselection. Unknown submissions remove writes while allowing deliberate current-order observations, including when VM readiness changes. Retain the last good observation after read failure; reads never unlock a consumed request. Preserve independent related-config invalidations and agent/location/mounted guards. No persistent browser drafts, global styling, mascot or pinned-demo changes. Observations/reviews continue to identify their original guest/node.
