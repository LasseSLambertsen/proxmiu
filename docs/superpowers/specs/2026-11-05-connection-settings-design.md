# Edit saved connection settings

## Intent and scope

Users can rotate a saved Proxmox token/password, adjust certificate verification, or rename a connection without deleting its identity, guest metadata or retained history. This is a controller-selected next improvement under the user's standing delegated iteration and publication instructions. Existing React/Fastify/Zod/encrypted-store patterns remain; no dependencies, privileges, provider requests or real infrastructure actions are added.

## Approach

Removing/re-adding loses identity; permitting destination edits could silently retarget historical guests/tasks to another cluster. Add an explicit Edit action and focused settings dialog instead. Preserve id, host, port and createdAt; another destination requires a separate connection. Only name, authType, username, optional replacement secret and verifyTls are editable. Keep the existing add flow intact.

## API and persistence

- Authenticated `GET /api/clusters/:id/settings` returns public fields plus an opaque HMAC revision derived from all saved connection fields, including the encrypted credential. No plaintext/ciphertext credential is returned. Do not add revision fields to existing list/create responses unnecessarily.
- `POST /api/clusters/:id/settings/test` and `PUT /api/clusters/:id/settings` consume the same strict object: `{ revision, name, authType, username, verifyTls, secret? }`. Revision is a nonempty bounded string (max128); name is trimmed1..120; username is bounded1..256 and excludes whitespace/control characters and `=`; secret is optional, nonempty1..16384, never trimmed; authType is token/password; verifyTls is boolean. Unknown fields, endpoint/identity edits, empty replacement credentials and missing fields are rejected with fixed safe400 errors.
- Omitted secret preserves the saved credential only if authType and username are unchanged. Switching either requires an explicit replacement. Fixed endpoints use the saved host/port; no browser-supplied upstream location/headers/commands are accepted.
- Both actions compare the supplied revision before probing. Probes instantiate a fresh candidate client, honor its TLS/auth settings and only authenticate/read version and nodes. Reject redirects for these candidate requests, including password authentication, and require valid Proxmox version/nodes response shapes; HTTP200 alone is insufficient. Existing client behavior outside this settings workflow stays unchanged. Test returns only `{ok:true}`, never persists or changes the saved-client cache. No upstream body or raw upstream error is returned or logged. Save repeats verification; testing is not authorization to save a changed draft.
- After every awaited probe, re-read the connection and compare its revision before returning test success or committing. Concurrent edit/removal cannot overwrite a newer record or recreate a deleted one. Missing records404, stale revisions409 with explicit reload guidance; failed authentication/TLS/reachability502 with a fixed recovery message. Successful save returns public fields+new revision and invalidates the saved Proxmox client cache only after durable persistence.
- Update persists encrypted credentials atomically and restores in-memory state if writing fails. Identity/endpoint/creation timestamp, guest metadata and job history remain intact. Never expose existing or replacement secrets in response, errors, captured diagnostics or plaintext state.
- Block save (before and after probe) while a provisioning/update job with this clusterId has status running. Tests need not be blocked. Existing remote operations and open terminals are not cancelled; the dialog explains that open terminals keep their current session and old credentials must be revoked separately in Proxmox. Subsequent requests use the new client; no automatic infrastructure recovery/retry.

## Interface

Use the existing Connections row and dialog primitives, warm glass tokens, Geist, restrained amber/teal and accessible labels. Edit opens fresh saved settings with secret blank and help “Leave blank to keep the saved credential.” Show fixed host:port, name, auth choice, username, new token secret/password, TLS switch, Test and primary Save changes. Changing username/auth requires a new secret; no reveal of the old credential. Disable fields during pending test/save; clear test success on any draft change. Explicitly close on agent change; prevent a draft or late callbacks from acting on a replacement agent/connection.

Errors preserve the draft. Conflict offers deliberate Reload saved settings; do not reset on background refresh. Cancel and failed test/save leave the old connection intact. During an accepted pending Save, show Saving… and prevent Cancel, X, Escape or outside dismissal from hiding its completion; agent changes still close the old context and suppress stale callbacks. Fresh settings404 from an older agent shows actionable update guidance. Keyboard focus, loading, stale conflict, malformed/safe errors and390px layout (including long destinations) must work in both themes. The isolated read-only demo and shared mascot remain unchanged.

## Verification and limits

Meaningful RED→GREEN real-agent/local HTTPS tests cover old/new credentials and client caching, keep-secret changes, auth/username replacement rules, identity preservation, encrypted disk persistence/restart, strict schemas/auth/origin guards, failed test/save/TLS, concurrent edits/deletion across delayed probes, active-job admission and write-failure rollback. Browser fixtures cover blank secrets/omitted field, test invalidation, disabled pending fields, successful save refresh, preserved failure/conflict drafts and explicit reload, fixed destination, cancel, agent-change cleanup and desktop/mobile dark/light. One batched visual pass and at most one confirmation after material fixes. Required full tests/typecheck/normal+demo builds and fresh spec/security/quality review precede exact-head CI-gated publication. Real Proxmox compatibility remains unverified.
