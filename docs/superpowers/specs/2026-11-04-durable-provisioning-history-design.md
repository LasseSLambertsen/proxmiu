# Durable provisioning history

Continue the user's authorized iteration on setup functions. Lynx creation drafts are published in app PR #8 and site PR #5. The next existing roadmap item is durable provisioning and template-update history: users must be able to inspect their setup after agent restart.

## Decisions

Persist bounded diagnostic snapshots in a separate encrypted `jobs.json` journal under `PROXMIU_DATA_DIR`, using the agent's existing encryption key. Extending the central credential state would rewrite unrelated secrets for every log update; plaintext diagnostics could expose script output; this separate encrypted journal keeps those concerns apart. No raw requests, options, passwords, private keys, scripts or resume instructions are stored. Use a Job-field allowlist and redact known request and template-default secrets in logs, errors and free-form result notes before both API output and persistence. Unknown script output remains sensitive diagnostics and is protected by encryption at rest; nothing new is sent to an AI provider.

The journal keeps at most 50 jobs, at most 5000 log lines and at most 128 KiB of serialized UTF-8 data per job, retaining the newest diagnostic tail. Bound individual log lines to 4096 characters, other free text and step counts so normalization is linear and bounded; show truncation explicitly. Never evict an active job: remove oldest terminal jobs first, and reject new work before side effects if all slots are active. Persist initial registration synchronously before running any write/SSH command; checkpoint step transitions and terminal outcomes immediately and coalesce log-only writes for at most 250 ms. Snapshots use restrictive file permissions and atomic replacement with a flushed, unique temporary file. The previous good journal survives failed writes; stale temp files are never loaded.

A loaded running job becomes `interrupted`, with `interruptedAt` and fixed recovery guidance. Completed steps stay completed, its running step becomes interrupted, and unstarted steps become skipped. Do not invent a completion time or success, do not expose a green ready result for interrupted jobs, and never automatically resume, retry, create, delete, stop, SSH or execute commands while restoring history. Keep intended guest identity/node where known so users can check the real guest before deciding what to do. Finished jobs retain outcomes and deep links. No migration can recover jobs lost by older agents before this feature.

The journal follows the existing deployment model of one active agent process per data directory; multi-process coordination is outside this iteration. Keep existing GET `/api/jobs` array and GET `/api/jobs/:id` contracts, with additive interrupted/truncation/target metadata. Add authenticated GET `/api/jobs/status` to disclose persistence availability/warnings/retention without revealing journal contents or filesystem errors. A corrupt, oversized, unsupported or undecryptable journal is preserved, history is explicitly unavailable and new starts fail closed before external writes; other agent features remain available. A later persistence failure keeps live execution and diagnostics available, marks history degraded, and never changes an actual operation outcome into a fabricated failure/success. New work must successfully persist before acceptance. Restoration must not overwrite malformed history or silently report an empty successful history.

Activity shows retained provisioning/update history separately from native Proxmox history, interrupted outcomes, saved-tail limits and clear manual recovery guidance. Successful historical guest readiness is labeled as an outcome of that run, not a fresh health observation. Read errors are distinct from verified empty history. Use the existing warm-glass UI, plain text, keyboard/390px behavior and existing authenticated API client. No new dependencies, privileges, infrastructure actions or provider sharing.

Verification uses focused TDD, real temp files and codecs, fault cases, authenticated agent restart tests with synthetic fixtures, and desktop/phone browser fixtures. No real Proxmox host, paid AI request or real provisioning side effect is required. Keep all existing Lynx/creation/native-history behavior intact, then publish through the user's authorized publishing subagent after exact-head CI.
