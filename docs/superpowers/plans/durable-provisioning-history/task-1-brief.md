# Task 1: durable provisioning and update history

Read this first; it is your requirements. Read CLAUDE.md, project.md, design.md and the spec at `docs/superpowers/specs/2026-11-04-durable-provisioning-history-design.md`. ## Implement

1. Add a focused job-history module and shared server Job type; integrate the existing provision/update runner and job APIs. Preserve `/jobs` array and `/jobs/:id` detail compatibility. Add `/jobs/status` (static route) for availability/degradation/retention metadata, protected by existing hooks. Suggested shape `{available,writable,warning?,lastSavedAt?,retention:{maxJobs,maxLogLines,maxJobBytes}}`; align web types with the final contract.
2. Separate encrypted `jobs.json`, versioned strict schema, existing encrypt/decrypt/key in store.ts, no raw request/options/passwords/scripts or encryption keys. Atomic unique-temp 0600 writes, flush/close/rename, 0700 data directory, preserve old file on failure. Refuse oversized input before reading (12 MiB file ceiling; 8 MiB plaintext ceiling), bad version/schema/decryption, or untrusted extra data rather than silently resetting/overwriting. Other agent functions stay available; starts reject safely when journal cannot load. Known malformed file is never replaced automatically. Missing file initializes empty history normally.
3. Bounds: at most 50 records, newest tail of at most 5000 lines and 128 KiB serialized UTF-8 per record, log line max4096 characters. Bound other free text and step arrays; preserve meaningful identifiers. Make tail normalization linear (budget serialized line bytes from newest backward; avoid repeatedly serializing/removing one line from a giant log). Expose `logTruncated` and safe retention metadata. Evict oldest terminal jobs first; never active jobs; reject admission when all slots active, before writes/SSH. Preserve last good state when initial registration fails.
4. Existing job live writes are mutable; connect checkpoints for initial registration, step start/end, failure, success, resolved/intended guest target and log appends. Initial snapshot persists synchronously before any external mutation. Logs may coalesce at most250ms, with state/final flush immediate. A runtime checkpoint failure sets status warning but does not throw from stream callbacks/stop the operation or falsify its result. New admission still requires a successful save. Handle graceful shutdown flush without breaking existing signal termination; hard kills can lose only the last uncheckpointed tail, never trigger replay.
5. Loaded running jobs become `interrupted`, `interruptedAt` now, running steps interrupted, pending steps skipped, completed steps retained, no invented `finishedAt`/ready result. Fixed guidance: the guest or remote command may still exist/run; inspect it before starting again. Never resume/retry/SSH/write Proxmox during restore. Save recovered state atomically if possible, with explicit persistence warning on failure. Completed records retain outcomes, result details and stable IDs/deep links. Job `target` may capture trusted intended/resolved VMID,node,type,hostname once known, without claiming creation succeeded. Avoid targetless interrupted jobs where preflight already resolved identity.
6. Central redaction for persisted AND API job snapshots: known request password, secret-typed options including short values and template secret defaults, plus existing long-option heuristic. Scrub log/error/free-form result notes consistently. Never serialize the secret registry or raw requests. Existing runUpdate must redact secret template defaults too. Keep secrets only in ephemeral memory needed for execution/redaction. Unknown script output is still sensitive; encrypt diagnostics rather than asserting perfect generic secret detection. No added provider sharing. Preserve source IDs and no automatic action controls.
7. Activity: interrupted tone/icon/badge distinct from success/error; no spinner/poll forever for interrupted. Show interruption/recovery guidance, intended guest identity where known, log-tail truncation, persistence status/warning/retention and read errors distinctly from an empty list. Existing historical success is “Completed”/“Was ready when this run finished”, not current health; only successful result gets ready-style surface. Native Proxmox history remains separate. Use api/agentFetch, existing warm-glass UI and keyboard/390px behavior. Extend types and affected browser fixtures as necessary. Keep Lynx creation/chat behavior unchanged.
