## Backend contract and behavior

- Add GET /api/ai/setup-context?id=<connection>&node=<node>&type=<qemu|lxc>&vmid=<integer>. Validate using existing guest parameter rules. Require configured AI settings and authenticated agent. Resolve /cluster/resources to verify selected guest still exists on exactly that node; mismatch is an actionable 409, not a silent switch. Exclude templates.
- Return a bounded preview `{previewId,expiresAt,provider,model,target,context,before}`. Target is `{clusterId,node,type,vmid,name}` with a bounded name fallback. `before` is the existing GuestResourceSettings shape (including digest). `context` is the EXACT object that may be sent to the provider: guest type, current status, numeric allocation (cores, sockets, memoryMiB), onboot, editable/reason, a bounded day-history summary with actual sample count/time coverage/mean/peak CPU and memory if available. Do not send target names/IDs or digest to provider: server keeps those solely to bind proposal to the user's chosen guest. Preview UI identifies target locally and separately displays exact context. No names, IPs, host addresses, notes, descriptions, disk/network strings, logs, tokens or arbitrary raw config in context. A resource-setting read failure prevents preview; history failure allows preview with fixed safe unavailable message. Read history directly and normalize with existing helper, do not load extra config just for it.
- Cache the exact snapshot server-side with random opaque ID, maximum 100 entries, ten-minute expiry, injectable clock. Bind it to provider/model and credentials identity without exposing token; replacement key/settings must invalidate it. Do not silently refresh cached context at send time. Include provider/model in preview so sharing destination is explicit.
- Extend chatSchema to accept optional `setup: {previewId: string,consent: true}` strictly. No client context or scope. Missing/false consent, stale/unknown preview or changed provider/model/key rejects before any provider request. Ordinary `{messages}` remains valid. Resolve cache in route and call contextual chat helper; no need to change normal helper signature if clean separate function is easier.
- For setup chat, supply read-only evidence plus instructions to return JSON `{reply: string, proposal?: {cores:number,memoryMiB:number,onboot:boolean}}`. Model may answer without proposal. Enforce resourceSettingsSchema bounds/strict keys (minus digest) and require actual changed values and editable snapshot; proposal only valid when all three values present, no extra keys. Unsupported/malformed proposals must never produce an actionable response. Parse valid JSON including optional whole fenced JSON; malformed/plain responses may degrade to plaintext advice. Keep reply <=4000 chars AFTER JSON parsing; provider response limit stays bounded. Plaintext and JSON output are never HTML/Markdown execution.
- Return `{reply,proposal?}` where a valid proposal is enriched with trusted `{target,before,after:{cores,memoryMiB,onboot,digest}}` from cache. The model never chooses digest/target. No Proxmox write in AI route. Contextual system prompt states evidence time/limits and available supported confirmed operation, prohibits claims of executed actions, secret requests or destructive commands. Update ordinary and setup prompts to professional, composed, perceptive Lynx voice with restrained cunning flair. Keep technical clarity first.
- Existing PUT resource-settings supplies authoritative fresh digest, running/pending/topology/permission checks. If needed add selected-node existence checking there to ensure migrated/deleted/reused target cannot get a stale AI write; preserve existing callers.
